# Project Memory

Last updated: 2026-07-09

## Current Architecture

- `apps/web` is the student-facing Next.js app.
- `apps/admin` is the admin CMS.
- `apps/api` is the Express + Prisma API and is the main place for backend feature work.
- Bunny Stream is the video delivery layer.
- Bunny Storage is used for master MP4 archives.
- Supabase/Postgres stores metadata only.

## Agent Knowledge Workflow

- `graphify-out/` is for generated code graph knowledge only.
- Durable project learnings belong in `docs/project-memory.md`.
- Stable agent operating rules belong in `AGENTS.md`.
- SkillOpt-Sleep is configured through npm scripts (`skillopt:status`, `skillopt:dry-run`, `skillopt:harvest`, `skillopt:run`) and targets the repo-local seed skill at `.agents/skills/cbse-project/SKILL.md`; keep `.skillopt-sleep/` untracked because it can contain harvested session review data and staged proposals.

- `.codex/hooks.json` delegates git-push checks to `.githooks/pre-push` for agent-driven pushes.

## Scaling Notes

- Curriculum source of truth for Class 10 subject definitions lives under `apps/web/lib/curriculum`, with session-aware sources in `official-sources.ts`, active lookups in `registry.ts`, validation in `validation.ts`, coverage formulas in `coverage.ts`, and per-subject data in `subjects/class-10/*.ts`.
- Curriculum session history is structurally immutable: each subject definition imports an explicit per-session module such as `apps/web/lib/curriculum/sessions/2026-27.ts`, while `registry.ts` separately selects the active session. Official-source records keep their own session and verification date.
- Historical sample papers and board paper archives can support comparison, but they must stay explicitly historical and cannot silently define the active blueprint for the current session.
- Official source eligibility is explicit through source role, subject-code applicability, session, source type, `mayDriveCurrentCurriculum`, and `mayDriveCurrentBlueprint`. Science, English, and Hindi remain available current subjects while their 2026-27 blueprint readiness is blocked because the registered PDFs embed 2025-26 paper-design evidence.
- Core curriculum coverage is topic-level. `CurriculumTopic.platformContentRefs` maps official topic IDs to chapter-pack or exact lesson evidence; board coverage ignores internal/formative, project-only, periodic-only, supporting-resource, and excluded topics even when they share a platform pack.
- Coverage dimensions use `complete`, `incomplete`, `not-configured`, and `not-applicable`. Empty denominators or absent publication/question evidence never report 100%, and board-paper seed readiness is not applicable to internal HPE.
- HPE follows the official internal structure and weighting: Games / Sports 50, Health and Fitness 25, SEWA 25, and Health and Activity Card 0. Existing packs are mapped as internal topics or supporting resources rather than board chapters.
- Words and Expressions - II is classified exactly: Units 1-4 and 7-11 are supporting resources, Units 5-6 are excluded, and missing platform files for Units 10-11 remain explicit readiness blockers.
- Mathematics Basic is a hidden `future` subject until a separate activation review is completed.
- Subject pages render official curriculum chapter titles, scopes, and topic scopes from the registry; legacy `course-content.ts` topic strings are platform metadata, not official 2026-27 scope.
- The student subject pages consume the registry instead of hard-coded subject lists: `apps/web/app/subjects/page.tsx` uses `getVisibleCurriculumSubjects()` plus `buildSubjectCatalog()`, and `apps/web/app/subjects/[slug]/page.tsx` resolves a registry subject before rendering mapped chapter routes.
- This repository's Graphify artifacts and skill expect `0.4.23`, while the installed package is `0.8.47`. `graphify update .` can produce incompatible broad drift in that state; record the warning and restore only generated Graphify drift until the versions are intentionally aligned.
- Lesson-wise chapter content is considered live only when a catalog lesson has a non-empty `fileName` and its chapter directory is registered in `lessonDirectories`. UI counts and previous/next navigation use available lessons only, while unpublished catalog lessons remain visible as Coming soon.
- Pilot chapter entry points should make the first live lesson the primary CTA, and pilot chapter cards should prefer lesson-level topic labels so the free pilot feels guided instead of catalog-like.
- Chapter content QA now uses `docs/content-style-qa-checklist.md`; pilot-ready chapters should pass easy scanning, short sections, example-after-concept, memory trick where useful, common mistake, board tip, practice prompt, and recap checks before widening access.
- Agent notes/content work now has a root `NOTES_GUIDELINES_STANDARDS.md` file. Read it before creating, reviewing, or editing lesson notes, chapter packs, quizzes, or Gemini animation integrations so prior mistakes around textbook numbering, parent-child section hierarchy, activities, figures, textbook `Questions` blocks with scoring-friendly answers, and quiz alignment are not repeated.

- Free-pilot quiz routes use strict authoring validation: every question must have a valid explicit answer, explanation, and chapter-matching topic slug before it can reach `QuizScoreForm`. Non-pilot generated quizzes retain the legacy parser fallback until their content is migrated.
- Keep route logic split by feature as new work lands.
- Defer payment/subscription logic until after a free student pilot produces real usage, feedback, bug fixes, and platform-hardening work. When payments return, keep them behind the same access helper path used by lesson video gating.
- Add gamification through event aggregation, not ad hoc counters inside request handlers.
- V1 gamification is planned as a personal Chapter Mastery Ladder: video completion contributes limited effort credit, quiz performance drives most mastery, low quiz scores create Revision Missions, and level rewards unlock revision tools rather than public competition.
- Mastery Ladder V1 stores raw quiz/video activity separately from `ChapterMastery`, so the score can be recalculated later if the video/quiz weighting changes.
- Gamification Phase 2 adds quiz-save aggregates through `StudyStreak`, `Badge`, and `UserBadge`: daily streaks use India calendar days, quiz badges are awarded for first quiz, score improvement, topic mastery, and comeback after a weak score, and newly earned badges are returned in the quiz-save response for the celebration UI.
- Saved quiz attempts are locked for review after answers are revealed; students should not be able to correct a revealed answer and resubmit the same attempt. Active revision missions should be completed or hidden once the student's best quiz score reaches the mission target, so dashboards do not show stale weak-score missions beside high mastery.
- Quiz Attempt Lifecycle V1 treats every retry as a new immutable saved attempt. The quiz page loads prior attempts, shows best/latest score history, and uses a separate retry action that clears local answers instead of re-enabling submit on a revealed attempt.
- Production quiz saves can exceed Prisma's default 5s interactive transaction timeout because the serializable save path also updates mastery, streaks, revision missions, and quiz badges. Keep `apps/api/src/routes/progress.ts` using explicit quiz transaction `maxWait` and `timeout` options, and treat `P2028` as retryable for this wrapped save flow.
- Pilot quiz weak-topic slugs come from the web lesson-wise content, while older production DB topic rows may still use grouped slugs such as Chemical Reactions `reaction-types`. API quiz-save validation should accept known pilot lesson slugs for weak-topic tracking instead of requiring every weak-topic slug to match a DB `Topic.slug`.
- If Two Stories quiz saves return `Chapter was not found`, check production `GET /v1/catalog/pilot`: on 2026-07-01 the web content was deployed but the production DB had not applied the free-pilot catalog migration, so English and `two-stories-about-flying` were absent until `prisma migrate deploy` applied the pilot catalog rows.
- Mastery Reward Unlock V1 is a personal, non-competitive surface derived from existing mastery scores and badge data. `apps/web/lib/mastery-rewards.ts` maps Learner, Skilled, Exam Ready, and Topper Track thresholds to locked/unlocked study-tool rewards for the dashboard and chapter pages.
- The Real Numbers quiz route depends on `apps/web/content/real-numbers/lessons/quiz.md`; keep at least one chapter quiz markdown file committed so the deployed quiz page does not 404.
- Quiz coverage is expected for every catalog chapter returned by `getChapterEntries()`. The web quiz loader first checks explicit quiz directories, then falls back to `apps/web/content/<chapter-slug>/lessons/quiz.md` so generated chapter-pack slugs can have quizzes without extra route wiring.
- Vercel serverless tracing must include `apps/web/content/**/*` for `/chapters/[slug]/quiz`; otherwise local quiz routes can pass while deployed fallback quiz markdown returns 404.
- Lesson pages should still render notes and embedded figures when the local API is offline; `apps/web/lib/lesson-video.ts` treats video fetch failures as `not-configured` so the video placeholder appears instead of a full lesson-page 500.
- Lesson navigation performance depends on keeping non-critical work out of the route shell: science activities use static image assets instead of canvas animation chunks, lesson video and quiz-history lookups stream behind `Suspense`, chapter mastery streams without blocking the chapter overview, and `app/loading.tsx` supplies immediate feedback for dynamic route transitions.
- The student quiz page parses numbered markdown questions into selectable answer cards. Add `Answer: <option number>` after options whenever the correct option is not option 1, because unkeyed generated quizzes currently fall back to option 1 for scoring.
- Quiz markdown now supports optional per-question `Topic:`, `Difficulty:`, `Source:`, and `Explanation:` lines through `apps/web/lib/quiz-content.ts`. `Topic:` drives weak-topic tracking only when it matches a valid chapter topic/lesson slug; explanations render after a locked submission for review.

The script resolves `content/` relative to its own file, so `npm.cmd run validate:quizzes -w apps/web` works even if the workspace cwd handling changes later.
